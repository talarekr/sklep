# Ovoko → Woo Gmail draft update — technical report

## Scope and safety decision

This document covers the requested separate module `Ovoko → Woo Gmail draft update` for the GPSwiss Ovoko integration plugin only. The change is intentionally limited to analysis and an implementation plan because the feature crosses product write paths, publishing rules, image safety, category rebuilding, Ovoko API reads, and batch UI. The first implementation should be done as a guarded service plus admin UI after the mapping extraction described below.

Hard boundaries for the implementation:

- Work only inside `wp-content/plugins/gpswiss-ovoko-integration`.
- Do not call eBay or Allegro flows.
- Do not create Woo products in this module.
- Do not import, overwrite, reorder, delete, or regenerate images.
- Do not touch products outside the Gmail/Ovoko flow.
- Do not publish unless the existing Woo product is eligible, the Ovoko data is ready for sale, the update succeeds, and existing Gmail images are still present and unchanged.

## 1. Current Ovoko → Woo create/import flow

The current manual Ovoko/RRR-to-Woo create flow lives primarily in `OvokoIntegrationService::preview_woo_product_create_from_rrr_part()` and `OvokoIntegrationService::create_woo_draft_product_from_rrr_part()`.

Current create flow summary:

1. Build an `RrrApiClient` from plugin settings.
2. Fetch a single Ovoko/RRR part by ID.
3. Normalize the raw payload.
4. Enrich normalized part data with vehicle data.
5. Try to match an existing Woo product by Ovoko identifiers.
6. Build a Woo title using the current title builder.
7. Validate that the product can be created.
8. Insert a new Woo `product` post as `draft`.
9. Write SKU, price, Ovoko meta, vehicle meta, part-number meta, same-vehicle meta, custom attributes, and product type.
10. Import Ovoko images and generate/listing-image metadata.

Important implication for the Gmail update module: the existing create method is not safe to call directly because it calls `wp_insert_post()` for a new product and then imports/replaces product images. The reusable parts are the fetch/normalize/enrich/title/meta/category/attribute routines, not the create method as a whole.

## 2. Existing classes and mapping responsibilities

### API fetch and normalization

- `RrrApiClient` is the read client for Ovoko/RRR diagnostics and product data.
- The create flow currently uses `preview_fetch_single_part()` followed by `normalize_rrr_single_part_payload()`.
- Vehicle enrichment is orchestrated by `OvokoIntegrationService::enrich_with_vehicle_data()` after normalization.

### Existing-product matching and generic Ovoko meta preview

- `OvokoProductSyncService` contains identifier matching helpers and Ovoko meta preview/change detection.
- It currently checks part IDs in `_ovoko_part_id`, `ovoko_part_id`, and `part_id`, plus several external-source keys.
- Its `preview_update_existing_product()` is currently a preview-only meta-change wrapper, not a full Woo product updater.

### Title, meta, attributes, vehicle data

- Title generation is handled by `build_woo_product_title_from_rrr_part()` and `build_woo_product_title_from_ovoko_part()`.
- Part/vehicle/meta mapping is embedded in the create flow and in `build_rrr_single_part_woo_meta_preview()`.
- Technical attributes are generated by `build_ovoko_technical_attributes_from_normalized()` and applied by `upsert_custom_product_attributes()`.
- Same-vehicle grouping meta is handled by `write_same_vehicle_meta_for_ovoko_product()` and related helpers.

### Category mapping

- Category path creation for manual live/import flows is handled by `ensure_manual_live_product_category_path()`.
- Existing category rebuild/update tooling already has a single-product path in `update_single_woo_category_from_ovoko()` and batch orchestration in `update_woo_categories_from_ovoko()`.
- The Gmail update module should reuse or extract category path resolution so it can map an Ovoko category to Woo without invoking unrelated global category rebuild behavior.

### Description mapping

- Current create flow uses Ovoko normalized `notes` as both `post_content` and `post_excerpt`.
- Separate description enrichment exists in `update_woo_description_from_ovoko_listing_text()` and `update_single_woo_description_from_ovoko_listing_text()`.
- The Gmail update module should use one extracted description builder that can decide between normalized notes, listing text, and existing shop logic without calling the Allegro-specific enrichment entry points.

## 3. Where images are imported today

Images are imported by `OvokoIntegrationService::import_ovoko_images_for_product()`. That method builds an image plan, downloads/sideloads Ovoko images, writes `_thumbnail_id`, writes `_product_image_gallery`, and may use the Woo product API to set featured/gallery images.

The create flow calls:

- `import_ovoko_images_for_product()`
- `generate_listing_image_for_ovoko_product()`

Both are unsafe for the Gmail update module. They must not be called from `update_existing_product_from_ovoko`.

The update module should take a pre-update image snapshot of at least:

- `_thumbnail_id`
- `_product_image_gallery`
- Woo product image ID
- Woo gallery image IDs
- attachment IDs currently attached to the product, if needed for diagnostics

Then it should compare the snapshot after the product update. If any image key changed, the update must be reported as failed and must not publish.

## 4. Proposed `update_existing_product_from_ovoko` architecture

Add a new dedicated service, for example:

`src/Services/OvokoGmailDraftUpdateService.php`

Public methods:

- `preview_eligible_gmail_drafts(array $options): array`
- `update_gmail_drafts_from_ovoko(array $options): array`
- `update_existing_product_from_ovoko(array $options): array`

Core options:

```php
[
    'target_product_id' => 0,
    'ovoko_part_id' => '',
    'preserve_existing_images' => true,
    'skip_image_import' => true,
    'publish_when_ready' => true,
    'do_not_create_new_product' => true,
    'dry_run' => true,
    'batch_size' => 10,
    'product_id_from' => 0,
    'product_id_to' => 0,
    'imported_after' => '',
    'imported_before' => '',
    'updated_status' => '',
    'stop_on_first_error' => false,
]
```

Recommended extraction before implementation:

1. Extract `build_rrr_single_part_product_mapping(array $normalized, array $payload, array $vehicleDebug): array` from the create flow.
2. Extract `apply_rrr_single_part_mapping_to_existing_product(int $productId, array $mapping, array $options): array`.
3. Keep `create_woo_draft_product_from_rrr_part()` as a thin create wrapper that uses the extracted mapping, but still owns `wp_insert_post()` and image import.
4. Make the Gmail update service call only the extracted mapping and existing-product applier with `skip_image_import=true` and `do_not_create_new_product=true`.

This prevents mapping drift while preserving the hard safety rule that the Gmail module cannot create products or touch images.

## 5. Image safety design

The Gmail update service should enforce image safety at three levels:

1. **No image methods called**: never call `import_ovoko_images_for_product()`, `sideload_ovoko_image()`, or `generate_listing_image_for_ovoko_product()`.
2. **No image meta writes**: the product applier must reject writes to `_thumbnail_id`, `_product_image_gallery`, listing-image meta, or attachment meta.
3. **Snapshot verification**: compare before/after image snapshots; if anything changes, mark the row as `failed`, add `images_changed_unexpectedly`, and do not publish.

Required result flags:

- `preserve_existing_images = true`
- `skip_image_import = true`
- `images_preserved = true|false`
- `image_snapshot_before`
- `image_snapshot_after`
- `image_diff`

A product with no existing Gmail images should receive `missing_existing_images` and must not publish.

## 6. Ready-for-sale validation

Create a validator method, for example:

`validate_ready_for_sale(int $productId, array $normalized, array $mapping, array $imageSnapshot): array`

Blocking reasons:

- `missing_price`
- `missing_category`
- `missing_title`
- `missing_description`
- `missing_part_code`
- `missing_existing_images`
- `ovoko_not_ready_for_sale`
- `not_gmail_ovoko_flow`
- `ovoko_fetch_failed`
- `update_failed`
- `images_changed_unexpectedly`

Minimum publish conditions:

- Product is an existing Woo product.
- SKU starts with `GPS-GMAIL-`.
- `_ovoko_part_id` or `ovoko_part_id` is present.
- Ovoko fetch and normalization succeeded.
- Price maps to a positive Woo price.
- Category ID/path maps to a Woo category.
- Title is non-empty.
- Description or generated description is non-empty.
- Manufacturer/visible/part code is non-empty.
- Existing Woo images are present.
- Image snapshot is unchanged after update.

The validator should be used in both preview and live update so dry-run and live decisions match.

## 7. Safe publication rules

Publication should happen only after a successful live update and only when `publish_when_ready=true`.

Live update sequence:

1. Confirm product eligibility.
2. Capture image snapshot.
3. Fetch and normalize Ovoko part.
4. Build mapping.
5. Run ready-for-sale validation before update for preview fields.
6. If not dry-run, apply safe fields to the existing Woo product.
7. Re-read product and image snapshot.
8. If update failed or images changed, mark `failed` and do not publish.
9. Re-run ready-for-sale validation with the final state.
10. If valid and `publish_when_ready=true`, call `wp_update_post()` with the same product ID and `post_status='publish'`.
11. Save status meta.

If not ready, the product should remain or be set back to `draft` only when it was already a Gmail draft/update candidate. The preview can show non-draft products, but the live updater should avoid changing statuses outside the explicit Gmail/Ovoko flow.

## 8. Finding eligible Gmail/Ovoko products

Use a constrained `WP_Query` or SQL query for `product` posts with:

- `_sku` meta `LIKE 'GPS-GMAIL-%'`
- at least one of `_ovoko_part_id` or `ovoko_part_id` not empty
- optional `_gps_ovoko_crm_only_imported_at` date bounds, if present
- optional product ID range
- optional `_gps_ovoko_update_status`
- `post_status` default `draft`, with preview option to include `any`

The single-product updater must re-check eligibility even when a product ID is passed manually.

Eligibility helper example:

`is_gmail_ovoko_flow_product(int $productId): array`

Returned fields:

- `eligible`
- `sku`
- `ovoko_part_id`
- `current_status`
- `has_crm_only_import_meta`
- `reasons`

## 10. Meta/status writes

On each live check/update, write:

- `_gps_ovoko_update_from_part_id`
- `_gps_ovoko_update_last_checked_at`
- `_gps_ovoko_update_last_success_at`
- `_gps_ovoko_update_status`
- `_gps_ovoko_update_blocking_reasons`
- `_gps_ovoko_update_published_at`, only when published
- `_gps_ovoko_update_preserved_images = yes`

Allowed statuses:

- `ready_to_update`
- `updated_draft`
- `updated_published`
- `blocked`
- `needs_review`
- `failed`

Dry-run must not write any of these meta values.

## 11. Batch and dry-run behavior

Dry-run behavior:

- Query candidates.
- Fetch Ovoko data.
- Build mapping and diff.
- Validate readiness.
- Return `would_update`, `would_publish`, block reasons, and diff.
- Do not call `wp_update_post()`.
- Do not call product save APIs.
- Do not update meta.
- Do not touch images.

Live batch behavior:

- Process up to `batch_size` candidates.
- Stop early if `stop_on_first_error=true`.
- Never create new products.
- Never call image import/generation methods.
- For each row, write status meta and result counters.

Summary counters:

- `eligible`
- `missing_ovoko_part_id`
- `not_gmail_sku`
- `already_updated`
- `updated`
- `published`
- `kept_as_draft`
- `failed`
- `skipped_images_preserved`
- `category_updated`
- `price_updated`
- `details_updated`

## 12. How to test on one product

Initial manual test should run only in dry-run mode:

1. Pick one Woo product ID whose SKU starts with `GPS-GMAIL-` and that has `_ovoko_part_id` or `ovoko_part_id`.
2. Run the admin preview with `batch_size=1`, `product_id_from=<ID>`, `product_id_to=<ID>`, `dry_run=on`, and `publish_when_ready=on`.
3. Confirm `would_update`, `would_publish`, block reasons, and image preservation fields.
4. Confirm featured/gallery image IDs remain unchanged after preview.
5. Run live update for the same single product only after preview looks correct.
6. Confirm no new Woo product was created.
7. Confirm `_thumbnail_id` and `_product_image_gallery` are unchanged.
8. Confirm publish happens only if all ready-for-sale checks pass.

## 13. Proposed implementation order

1. Add `OvokoGmailDraftUpdateService` with eligibility query, single-product preview, ready validator, image snapshots, and dry-run result model.
2. Extract mapping from `create_woo_draft_product_from_rrr_part()` so create and update share one mapping source.
3. Add safe existing-product applier with explicit denylist for image/meta/attachment writes.
4. Add live single-product update with meta/status writes.
5. Add batch update and summary counters.
6. Add admin-page UI section and CSV exports.
7. Add tests for eligibility, validator block reasons, image snapshot diff, and dry-run no-write behavior.
8. Add a single-product manual smoke test in staging before enabling batch live updates.

## 14. Implementation recommendation

This should not be implemented as a small patch inside `create_woo_draft_product_from_rrr_part()`. The safe route is a new Gmail-specific service that reuses extracted mapping but owns its own guardrails. The most important implementation constraint is that image importing/generation and product creation remain impossible from the Gmail update code path, not merely disabled by UI convention.
